# FPVR

Modular ground-control app for flying a USB-connected GPS + ELRS + UVC-camera UAV setup from a Steam Frame VR headset, with Android-phone and Linux-PC shells sharing the same core. See the architecture plan for the full design rationale.

## Layout

- `core/` — GDExtension (C++/godot-cpp) native library: USB device discovery (serial + UVC, USB-only), NMEA GPS parsing, CRSF ELRS parsing/channel-packing, UVC capture, ATAK CoT message building. Build with `cd core && scons platform=linux target=template_debug` (desktop x86_64), `arch=arm64` added for Steam Frame — see Status below and the VSCode tasks.
  - UVC capture has two backends behind one interface: `UvcDriver` (V4L2, kernel-driven) is always preferred when a `/dev/videoX` node exists. `UvcUsbfsDriver` (direct `USBDEVFS_*` ioctls on the raw usbfs fd — the same mechanism libusb/libuvc use) is the fallback: the *only* option on Android (no built-in UVC support at all), and an automatic fallback on any Linux target — including Steam Frame — when a UVC device is on the bus but no `uvcvideo` kernel module is bound to it (`UsbDeviceRegistry` detects this via a sysfs walk). `HardwareHub` picks automatically and surfaces a warning in the Video and Telemetry windows when running on the fallback, since it's less latency-stable than the kernel driver.
- `app/` — Godot 4.7 project.
  - `core_services/` — shared GDScript glue: `hardware_hub.gd` (autoload; owns device discovery + live drivers, read by every window/shell — picks a Linux or Android backend automatically), `android_usb_source.gd` (Android's serial-port equivalent, backed by the plugin below), `control_mapper.gd` (flight input → CRSF channels), `passthrough_controller.gd` (IR/RGB/Black toggle), `settings.gd` (persisted settings).
  - `input/` — interchangeable flight-control sources: `steamframe_controller_input.gd` (OpenXR motion controllers), `generic_gamepad_input.gd` (BT/USB HID gamepad).
  - `windows/` — the four shared window scenes (video, GPS/UAV map, telemetry/status, settings), used unmodified by every shell (each shell toggles which settings rows are relevant to it).
  - `xr/` — VR-only pieces: XR rig, SubViewport-on-a-quad window wrapper, grab dispatcher.
  - `bridge/` — `atak_bridge.gd`, shares position/telemetry with ATAK on a companion phone as CoT over UDP.
  - `shells/` — `shell_linux_pc` (flat, windows side by side — primary dev/iteration target), `shell_vr_steamframe` (XR shell with grabbable windows + flight control + passthrough toggle), `shell_android_phone` (flat, tabbed, safe-area-aware).
  - `android/build/src/main/java/org/fpvr/plugin/FpvrPlugin.java` — the Android-platform plugin (see below).
  - `bootstrap.gd`/`.tscn` — the actual main scene; picks the right shell at runtime (VR shell only if an OpenXR session actually initializes, else the phone shell on Android, else the Linux/PC shell), so one APK works correctly on both a Steam Frame and a plain phone.

## Status

- Verified end-to-end on this dev machine: USB auto-discovery, NMEA GPS parsing, CRSF ELRS parsing + channel packing (against hand-built reference frames), UVC capture + JPEG decode (against a real USB webcam), ATAK CoT bridge (real UDP packets received and validated), all four window scenes, and all three shells booting cleanly.
- `shell_vr_steamframe` has **not** been run on real Steam Frame hardware (none available during development). It boots cleanly in flat fallback (no OpenXR runtime on this machine) and the scene graph/wiring is verified that way, but controller button/action names follow Godot's default OpenXR action map and should be checked against actual Steam Frame controller bindings on-device.
- **Android, tested live on a Pixel 10 Pro**:
  - Fixed an initial black-screen bug (the export preset was forcing OpenXR mode, which waits forever for a session a plain phone can never start) via the `bootstrap` runtime shell-selection described above.
  - Fixed the phone UI being clipped by the screen's rounded corners / too small to tap comfortably (safe-area-aware margins + larger touch targets in `shell_android_phone`).
  - Built `FpvrPlugin`, a Godot v2 Android plugin (Java), because stock Android blocks the raw `/dev` access the Linux backend uses (confirmed via repeated SELinux denials in testing). It exposes USB device enumeration/permission/CDC-ACM serial I/O via `UsbManager`, raw usbfs access for UVC (see below), and the phone's own built-in GNSS via `LocationManager`. `HardwareHub` picks this backend automatically on Android behind the same interface the Linux `SerialPort`/`UvcDriver` paths use, so `GpsDriver`/`ElrsDriver`/MJPEG-decode parsing is untouched — only the transport differs. When both the phone's internal GNSS and a USB GPS are present, whichever reports better accuracy wins.
  - **UVC video capture works on Android**, verified live against a real USB analog FPV receiver (not just a webcam): `UvcUsbfsDriver` (core) parses the raw UVC descriptors Android hands up, does the Probe/Commit negotiation, and streams isochronous URBs via direct `USBDEVFS_SUBMITURB`/`REAPURBNDELAY` ioctls on the raw fd — the same mechanism libusb/libuvc use on desktop Linux. Decoded MJPEG frames render in the Video window exactly like the Linux path. Getting here required finding and fixing three non-obvious platform bugs (all confirmed via on-device logcat, not guessed): Android won't show the USB permission dialog for a video-class device without `CAMERA` permission also granted; it drops a second permission-dialog request if one is already showing (now serialized through a queue in the plugin); and `PendingIntent.getBroadcast()` with `FLAG_MUTABLE` throws for an implicit intent on API 34+ (fixed via `setPackage()`) — that exception was being silently swallowed by Godot's JNI dispatch layer, invisible until a try/catch was added around the call directly. A fourth issue (raw `USBDEVFS_CLAIMINTERFACE` failing `EBUSY` even as the first attempt) was worked around by claiming the interface via Android's own `UsbDeviceConnection.claimInterface()` Java API before handing the fd to native code.
  - The CDC-ACM serial path (GPS/ELRS) has not yet been exercised against real serial hardware — only a UVC-class device was attached during Android testing so far.
  - Building the Android plugin requires Gradle's custom-build path: `godot --headless --path app --install-android-build-template` (installs the template into `app/android/`), `gradle_build/use_gradle_build=true` in `export_presets.cfg` (already set), and a JDK the Gradle version actually supports — the system default here was JDK 27, too new for Gradle 8.11.1 ("Unsupported class file major version 71"); pinned via `org.gradle.java.home` in `app/android/build/gradle.properties` to a JDK 21 install.
- Passthrough IR/RGB/Black toggling is implemented as best-effort: Valve has not published an API to distinguish stock monochrome passthrough from the third-party Arcturus color camera, so both currently issue the same OpenXR alpha-blend call.
- **Steam Frame's current OS doesn't ship the `uvcvideo` kernel module**, so `/dev/videoX` never appears for an attached UVC device there. `HardwareHub` detects this automatically (via a sysfs walk for USB video-class interfaces with no `video4linux` child) and falls back to `UvcUsbfsDriver`, with a warning shown in the Video and Telemetry windows. V4L2 is always preferred when available, including if `uvcvideo` is manually installed (as on this project's test Steam Frame unit) — kernel-driven capture is lower-latency and far more hardened against device quirks than the in-app driver. The fallback's descriptor-parsing and interface-claiming logic is verified against two different real UVC devices; the full open-to-streaming path specifically in "no kernel driver at all" conditions was not exercised live (the only available test device here has `uvcvideo` actively bound, and recreating the true unbound condition needed a further system change that wasn't pursued) — code-reviewed and built on the already-proven Android implementation, but worth a real check on an actual Steam Frame without the driver installed.
- **Steam Frame runs real Linux/SteamOS on an ARM64 (Snapdragon) SoC — not Android.** Neither the Android APK nor the x86_64 Linux build is correct for it; it needs its own export preset, **`"Steam Frame (Linux ARM64)"`** (`app/export_presets.cfg` preset 2), built from a GDExtension cross-compiled for `platform=linux arch=arm64`. Cross-compiling with the host's own `aarch64-linux-gnu-gcc` (e.g. `sudo pacman -S aarch64-linux-gnu-gcc aarch64-linux-gnu-binutils` on Arch/CachyOS) links against *this dev machine's* glibc, which is newer than what SteamOS actually ships — confirmed on real hardware: the exported binary ran, but the core library itself failed to load with `GLIBC_2.43' not found`. Fixed by cross-compiling with **`zig cc`/`zig c++`** instead (`sudo pacman -S zig`), explicitly targeting glibc 2.17 (the conservative "manylinux2014" baseline) rather than whatever glibc the host toolchain happens to bundle — the resulting library only requires `GLIBC_2.17` and has no libstdc++/libc++ runtime dependency at all (zig statically links its own). VSCode task "Core: Build (Linux ARM64 - Steam Frame)" sets this up automatically: `ar`/`ranlib`/`ld`/`strip`/`objcopy` stay the real `aarch64-linux-gnu-*` binutils (they don't link against target glibc, so the version mismatch never applied to them), while `clang`/`clang++` become wrapper scripts invoking `zig cc`/`zig c++ -target aarch64-linux-gnu.2.17`, picked up via `use_llvm=yes` — godot-cpp's own `tools/linux.py` already has a `use_llvm` path for clang-based toolchains, needing only two small accommodations confined to `core/SConstruct` (stripping the `-march=armv8-a` flag zig's clang frontend rejects outright, and overriding SCons' `.os` shared-object suffix to `.o`, which zig's driver doesn't recognize by extension — the same workaround godot-cpp's own `web.py` tool already uses for Emscripten). Build + export via the "Export: Steam Frame (Linux ARM64)" VSCode task, producing `builds/steamframe/fpvr.arm64` — verified as a genuine ARM64 ELF binary built from Godot's own official ARM64 Linux export templates, with the core library's glibc requirement confirmed via `objdump -T`, but **not yet fully runtime-tested end-to-end on actual Steam Frame hardware** past confirming the library now loads (the dlopen failure above was caught via real on-device testing; later functional testing is still in progress).
